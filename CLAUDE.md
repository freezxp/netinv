It was also the first component accepting unsolicited network input (doc 34 §6); `netinv-events` (traps, below) is the second on both counts.
- **Flow collection is live on the pilot (ADR-020/022, doc 34).** `netinv-flow` decodes **NetFlow v5, v9, IPFIX and sFlow** (ADR-022, ADR-026) on UDP 2055, 4739 and 6343, and aggregates at ingest into top-N talkers/conversations/applications per interface — `netinv_flow_bytes` and `netinv_flow_packets`. Raw per-flow storage stays deferred; a bucket outside the top N was never written, not merely unqueried. sFlow needs its own decoder and shares none of the template machinery. The **Flow tab** on device detail and the **Top flow** dashboard panel read the series through the metrics proxy — note `netinv_flow_bytes` is *not* cumulative, so `rate()` silently under-reports it; use `flowRateExpr`/`flowWindow` from `api/hooks.ts`. The per-vendor exporter setup guide is duplicated in doc 34 §4.2 and `features/devices/FlowSetupGuide.tsx`; change both together. **A pilot UniFi gateway now exports NetFlow v5 and it decodes end to end** (2026-08-12, doc 34 §4.2) — the first real-hardware flow validation. UniFi Network has native flow export under Traffic Logging (v5/v9/IPFIX); the earlier claim here and in doc 34 that UniFi *cannot* export flow was inferred from a missing sFlow MIB and was simply wrong. Two of its defaults matter: sampling is **on** (Hash 1-in-512) and Timeout Rate — the active timeout — is 5 minutes, so exports arrive in bursts. Turning sampling off took the pilot from 7 minutes of data in 45 to 27 in 30. **Flow totals are a fraction of the SNMP counters and that is by design** — measured at 3.3%/10.5% on two interfaces, dominated by the top-N cut, which was confirmed saturated at its ten-bucket cap in every interval. Sampling scale is verified against captured headers (`mode=2 interval=512` sampled, `mode=0 interval=0` off), so the gap is ADR-020's design, not a decode error: SNMP is the authority for volume, flow for composition. Export is selected **per network**, not per interface, and an unticked network is silently absent. Gateways export from their **WAN address, not their management IP**, so devices carry a `flow_exporters` list (doc 34 §3.1) that the Flow tab can claim addresses into; building a multi-address selector needs `reQuote` from `api/hooks.ts`, because MetricsQL unescapes the string before compiling the regex and a single backslash is rejected as an invalid escape. v9, IPFIX, IPv6 and options-record sampling are still validated only against a generated source. The two firewall connectors from ADR-021 both export v9 and can now feed it — a real exporter is the most useful thing an outside contributor could test. **v9 and IPFIX make the collector stateful** — a data record is meaningless without the template describing it, so a restart loses every template and flow stays missing until exporters resend (10-20 min). That window is counted as `awaiting_template`, deliberately *not* as "undecodable", so nobody hunts a fault that is not there. Three traps cost time and are worth knowing: VictoriaMetrics hides samples newer than 30 s from instant queries (`-search.latencyOffset`), so a "did my write land" check right after a drain returns zero and looks like a broken writer; and the collector is deliberately quiet when idle, so "no log output" means nothing is arriving, while a misconfigured exporter logs `flow intake` at info. **Confirm "nothing is arriving" at the wire with a capture longer than one active timeout** — the UniFi default is 5 min, so a 90 s `tcpdump` can fall between bursts and read as silence; `printf 'PROBE' > /dev/udp/<host>/2055` should produce `flow intake … undecodable:1`, which proves the receive path is live.
- **Flow stops silently, and two built-in alert rules now exist because of it (migration 0012, doc 34 §5.1).** On 2026-08-17 all three pilot exporters were found dead — two of them (both remote sites) had stopped *within a minute of each other 42 hours earlier* and nobody noticed, because the third kept exporting and every fleet-wide flow query stayed non-empty. **Partial loss is the case worth alerting on**; "is any flow arriving" stays green through it. `ar_flow_exporter_stale` subtracts exporters seen in 20 min from those seen in 7 d, so it fires once per stale exporter with the `exporter` label, covers total loss too, and self-gates on deployments that never ran flow. `ar_flow_absent` extends past 7 d and **must keep its `and on() count(last_over_time(…[30d]))` gate** — bare `absent_over_time` returns 1 for a metric that never existed, so ungated it fires on every install without flow. Both windows are ceilings past which the alert resolves while the fault persists; the fix that removes them is an inventory-derived `netinv_flow_exporter_expected` from `devices.attrs->'flow_exporters'`, blocked only because `netinv-flow` has no database access. The root cause of the outage itself was exporter-side, not NetInv: collector listening, zero restarts, no audit change, and SNMP from the same gateways unaffected.

- **If you touch `scripts/restore.sh` or judge a restore:** verify by comparing data at a timestamp *inside* the backup window, never by exit code and never at "now" — a good restore's newest sample is the snapshot instant, so an instant query at now under-counts series and looks like a failure (it read 78 vs the live 226 during the drill). And `NETINV_MASTER_KEY` is deliberately not in the backup: without it a restore yields inventory and history but no usable credentials.
- **ifIndex is not stable, and nothing may pin it.** Agents renumber across reboots: a pilot gateway moved `ppp2` from ifIndex 76 to 41 on 2026-08-15. Two consequences, both fixed and both worth remembering. The unique constraint on `(device_id, if_index)` is now **partial on `state='present'`** (migration 0011) and `Apply` retires-then-parks-then-writes (doc 11 §3.1) — the old unconditional constraint made a legal reindex unrepresentable, so the sync transaction aborted and, because sync results are requeued, **retried every second forever** while inventory silently froze at the pre-reboot topology. And the weathermap resolves a link's ifIndex from `maps.map_links`' stable interface row id at render time, treating the value saved in the map document as a fallback; before that, a renumbered interface left the link reading `nodata` while the interface itself carried 6 Mbps. **Diagnose a frozen inventory with `docker logs netinv-api-1 | grep "sync result requeued"`** — a repeating `duplicate key ... interfaces_device_id_if_index_key` is this bug.
- **Since v1.1.0 (2026-08-18/19) the product grew four things worth knowing before you go looking for them.** **Interfaces** (`/interfaces`) searches every port in the fleet by ifAlias, ifDescr, ifName or customer — alias is the field operators curate and it was previously readable one device at a time. **Reports** (`/reports`, `GET /reports/bandwidth`) answers what a set of interfaces *did* over a closed period: avg / p95 / peak bits/s per direction, bytes, utilization, CSV export, optionally **one row per customer**. **Interface customer + tags** (migration 0017) are operator-owned columns sync never writes, assignable in bulk by CSV (`POST /interfaces/tags`, matching devices by name or address and ports by name or ifIndex, reporting unmatched and ambiguous rows rather than guessing). And the **weathermap generator** (`POST /maps/generate`) draws a draft from LLDP adjacencies — it refuses on the pilot, whose gateways are joined by WireGuard and report no LLDP at all.
- **Two report invariants that are easy to break and impossible to see broken.** A customer's p95 and peak are of their *combined* traffic, so the sum happens **inside the query** (`sum by (dir)` per group, labelled, then the rollup); adding per-interface peaks assumes every circuit peaked at once, and adding p95s is not a percentile of anything. And per-interface selectors are unioned with `device_id` **exact** and only `if_index` a regex — patterns on both sides match the cross product and would sweep one customer's port on another customer's device into their total, invisibly, onto an invoice. VictoriaMetrics caps a query at 16 KiB (`-search.maxQueryLen`), which a fleet-wide grouped report hit at 49 KiB: selectors are collapsed per device and groups batched under the limit, but **a group is never split**, because a partial sum cannot be rolled up correctly.
- **`upgrade.sh` pulls by default and preflights the disk.** `deploy/compose-app/upgrade.sh` derives its compose invocation from the running containers' labels, so it cannot half-recreate the stack the way a bare `docker compose` does. It fetches and fast-forwards before building (`--no-pull` to skip, `--latest` to make a failed pull fatal — use that in automation), backs up first and prunes to `--keep 3`, and refuses up front when the disk cannot take it. **The disk check asks Docker where its root actually is and checks containerd's root too**: with the containerd snapshotter — the default now, and what both deployments run — image layers live under `/var/lib/containerd`, so `df /var/lib/docker` is a reassuring answer to the wrong question. That exact configuration cost a real deployment several rounds of diagnosis with BuildKit reporting only `exit code 1`.
- **A device that never leaves `pending` is silent by default, and there are four separate reasons for it.** A device is promoted to `active` in exactly one place — the sync apply transaction — so ICMP, traffic and health polls can all succeed, graphs and all, while the device never onboards. The four causes are: the polling profile omits `sync` from `families_enabled` (the schedule row is *deleted*, so nothing is dispatched); no poller consumes the device's site queue (jobs accumulate unread, nothing logged); SNMP failed (reason on the run row); or collection worked and the apply is requeuing. Since 2026-08-18 the device page carries the diagnosis — a banner above the tabs and the sync-run list on History, via `GET /devices/{id}/sync-runs` (doc 09, doc 30 §5). **The no-consumer case is now detected rather than guessed**: the scheduler declares every site queue before publishing to it and `queue.declare` returns the consumer count, which it records per site (migration 0013, `platform.site_collection_health`) and warns about once on the transition. That signal was chosen over a poller-heartbeat one because `platform.pollers` is *empty* on the pilot — it runs the poller in local mode with `NETINV_SITE_ID` and never enrols, so a heartbeat-derived check would report "no poller" for every site on the flagship deployment. Before that `platform.sync_runs` was written on every poll and read by nothing, so the recorded reason was reachable only from psql. `scripts/diagnose-pending.sh` tells the four apart from a shell and is the tool for a deployment whose UI you cannot reach; doc 31 §9 carries the same table.
- **A device can answer everything and still have no graphs: check `netinv_if_counters_repaired`.** Some SNMP agents walk the ifTable config columns for every interface and then return almost nothing for the counter columns, while a GET for those exact OIDs answers correctly — the traversal is broken, not the data. The generic connector now repairs the gap with batched GETs (doc 10 §7) and publishes the repaired-varbind count, **zero on a healthy agent**. A pilot UniFi gateway entered this state on 2026-08-14 15:35 UTC and sat there for seven hours looking perfectly healthy: ICMP up, poll_success 1, inventory complete, 6 of 51 interfaces graphing. Repair took it back to 46 interfaces at 328 varbinds/poll while every other device reported 0. **Diagnose by comparing walk against GET** — `snmpwalk -c <community> <host> 1.3.6.1.2.1.2.2.1.10 | wc -l` versus `snmpget` on a specific `if_index`; a walk that returns far fewer rows than `ifOperStatus` is this bug. The device-side fix (restart snmpd / force-provision) is still worth doing, and a non-zero repair count is how you know it is needed.
- **A poller serves the sites it is told to, and `NETINV_SITE_ID=*` means all of them.** The list used to be maintained by hand, and it was the most reliable way to lose collection silently: create a site, move a device into it, and its jobs pile up in a queue nobody reads — publish succeeds, nothing errors, nothing is logged, the device is simply never polled. The scheduler now announces the active site list every 15 s on the `sites.active` fanout (`amqpx.SitesExchange`), and a poller set to `*` starts and stops per-site consumers to match. It is deliberately a full list rather than a delta, so a poller that missed a message or started late converges on the next one. Compose defaults to `*`; an explicit list is for a poller restricted to part of the estate. Diagnose the old failure with the device page banner ("No poller is collecting for site …") or `platform.site_collection_health` where `consumers = 0`.
- **Every AMQP consumer must cancel the one it replaces** (doc 07 §6.1). `amqpx.Consume` gives each consumer its own channel and returns a `stop` func; call it before looping round to reconnect. On the shared channel a retry registered an *extra* consumer, the broker round-robined jobs to one nobody read, and those sat unacked forever — the queue grew silently while the service kept processing the share that reached the live consumer. Found on the pilot 2026-08-14: one site had 3 consumers on its queue and its gateway was losing two polls in three while still reporting `poll_success` and drawing graphs. Fixing it took fleet ingest from 32 to 50 rows/s. **Diagnose with `rabbitmqctl list_queues name messages messages_unacknowledged consumers`** — a consumer count above 1 per site queue, or unacked with nothing ready, is this bug.
- **Judge collection health by `vm_rows_inserted_total`, not by query freshness.** `timestamp(last_over_time(m[10m]))` in an instant query does not advance reliably (VictoriaMetrics' `-search.latencyOffset` plus result caching), so it reads as a stall when everything is fine — it wrongly said "STALLED" during the 2026-08-14 redeploy. Scrape the counter twice and diff it: 232 interfaces on a 60 s cadence is ~32 rows/s. **Diff over at least two poll cycles** — a 20 s window landing between bursts read 0.9 rows/s on a fleet actually doing 28.5.
- **To decide whether a metric has stopped, use `/api/v1/export` — every other query form can lie, in both directions** (doc 34 §5.2). Diagnosing the 2026-08-17 flow outage, three forms each gave a confidently wrong answer about the same series: a `query_range` at `step=1800` reported a populated bucket 70 min after the last real sample, because the lookbehind is `max(step, 5m)` and a coarse step carries a stale value forward; a 7-day bucket scan reported **100% coverage** while flow had been dead 80 minutes, because a gap scan whose window ends at the last populated bucket is structurally blind to a *trailing* gap; and an instant query said "no data" for a healthy series inside the 30 s latency offset. `/api/v1/export` returns raw stored samples with timestamps — no fill, no lookbehind, no caching. Always compare the newest sample against `now` explicitly rather than trusting a coverage figure.
- **Recurring lesson worth reading before touching metrics code:** MetricsQL `or` matches on labels *excluding* `__name__`, so two metrics that differ only by name collapse into one and the second disappears silently. This has now caused three separate bugs (traffic in/out, memory used/total, AP up/total). Combine named metrics through `trafficExpr`/`seriesExpr` in `frontend/src/api/hooks.ts`, never a bare `or`.
- **Every flow is also stored, in ClickHouse (ADR-026, doc 34 §7, 2026-10-29)** — the aggregates above are unchanged and still drive the Flow tab, dashboard panel, stale-exporter alerts and `/flow/top|series|exporters`. `netinv-flow` hands each decoded packet to `flowstore.Writer` (bounded queue, never blocks intake, retries with a dedup token), which writes `netinv_flow.flows` (TTL `NETINV_FLOW_RAW_RETENTION`, default 30 d) and, via a materialized view, `flows_1h` (TTL `NETINV_FLOW_ROLLUP_RETENTION`, default 365 d; drops MAC/NAT/user/flags/next hop and folds ports ≥ 32768 to 0). The collector owns the schema (`flowstore.EnsureSchema`, no goose). The api serves `/flow/explore`, `/flow/records`, `/flow/explore/status` (doc 09 §7.2) to the **Flows** page (`/flows`, doc 30 §5c). Two ClickHouse traps that cost time: a SELECT alias shadows a column of the same name **inside WHERE** (so `… AS src_addr` broke address filters) — `Select` sets `prefer_column_name_to_alias`, and aggregate aliases carry an `m_` prefix; and a retried insert is deduplicated in a materialized view's target only if **that** table has its own `non_replicated_deduplication_window`. Interface group keys are `exporter|ifIndex`, because an ifIndex means nothing across devices. Country/AS-name enrichment reads files from `flow-geo/` (gitignored; `scripts/fetch-flow-geo.sh`, DB-IP credit required on screen). Raw flows are **not** backed up. **Validated against a local generator only**, as v9/IPFIX were — no real v9, IPFIX or sFlow exporter has reached the raw store. Integration tests need `NETINV_TEST_CH_URL` (+ `_USER`/`_PASSWORD`) and drop the `netinv_flow` database: never point them at a deployment.
- **SNMP traps are received (ADR-025, doc 36, 2026-10-21) by `netinv-events`, the eighth service** — single replica, UDP 162 on the host mapped to 1162 in the container, the second component after flow to accept unsolicited input. v1/v2c traps and v2c informs only; v3 and syslog stay deferred. A trap from a known device is stored in `events.snmp_traps` and written as `netinv_snmp_trap=1` (labels `trap`, `if_index`) through `metrics.raw`, so alerting is ordinary rules with a `max_over_time(…[10m])` window — migration 0019 ships `ar_trap_auth_failure` (warning) and `ar_trap_received` (info, excluding the link/restart traps polling already alerts on). Sources resolve by management IP, then the device's `flow_exporters` claims, then the v1 agent address; an unknown source is stored but writes no series. Trap names: RFC ones in `events/names.go`; Fortinet and Palo Alto in `names_vendor.go`, **generated** from MIB text by `scripts/gen-trap-names.py` — do not hand-edit, and note that no real FortiGate or PAN-OS trap has been checked against it yet. Validated against a net-snmp simulator only. **Adding a service needs an entry in `defaultHealthPorts` (`platform/config`)** or it exits with `config: unknown service`.
- **Other applications read NetInv with API tokens, and flow has an API of its own (2026-10-23, doc 09 §3 and §7.1).** `nv_` tokens are minted under Platform → API tokens or `POST /users/me/tokens`, stored as SHA-256 only, and sent as an ordinary `Bearer`; `authn.Chain` routes them by prefix to `iam/app.APITokenService`. Effective permission is token scopes ∩ the owner's *current* roles, enforced in `httpx.RequirePerm` — **any new permission check must go through it**, or a scoped token will silently get the owner's full rights. Minting, revoking and password change refuse tokens (`httpx.RequireInteractive`). `GET /flow/top|series|exporters` (package `flowquery`, `metrics:read`) does the two things clients got wrong on the raw series: sums per-interval samples instead of `rate()`, and attributes exporters to devices. The collector now also writes `protocol`, `dscp`, `as`, `subnet` and `tcp_flags` dimensions (ADR-020 amendment, doc 34 §3); the UI's Flow tab does not show them yet. Doc 20 §9's per-token rate limit is **not implemented** — no rate limiter exists anywhere in the API.

Doc 25 §5.1 lists what is still unwired and why — OpenAPI drift is *blocked*, not pending, because no OpenAPI document exists.
- **Connector fixtures:** `scripts/record-fixture.sh` records an snmpwalk and redacts identity at capture time — values *and* table indices, since tables like the Ruckus per-AP one are indexed by MAC. `sdk/sdktest.Load` replays one as a Session. `generic`/`cisco` come from snmpsim (reproducible, no redaction); `ruckus`/`ubiquiti` from real hardware; `huawei`/`juniper`/`zte` have none because there is no hardware to record from.
- **Deployment settings that the UI and the API must agree on.** Three values are configurable and each has a coupling that breaks silently if it drifts:
  - `NETINV_VM_RETENTION` (default **2y**) is read by *both* VictoriaMetrics and the API — the API rejects range queries beyond it with 422 rather than clamping, so a ceiling below actual retention hides data the operator is paying to keep. Shipping the Cacti presets against a hard-coded 90-day ceiling made "Last Year" return an error instead of a chart; that is why they are one setting.
  - **Poll cadence** is editable fleet-wide from Platform → Pollers (1/5/10/15 min, `PUT /platform/polling`). It writes `polling_schedule` as well as the profile, because the scheduler reads the schedule. `rate()` lookbacks are sized from it — a lookback shorter than the cadence spans one sample and returns nothing, blanking every traffic chart with no error.
  - `GET /metrics/limits` reports both (`max_range_s`, `poll_interval_s`) so the frontend never hard-codes either. If you add a chart, size its rate window with `rateWindow(step, pollS)` from `api/timerange.ts`.
- **Graphs share one time range** (`api/timerange.ts`): Cacti's nineteen timespans, default "Last Day", persisted in localStorage, applied to every chart including the weathermap hover card. Step and rate window scale with the span. Presets past retention are shown disabled, not hidden.
- **Platform → Capacity** (`GET /platform/capacity`) answers "will the disk hold this retention": disk used/free, measured bytes-per-sample, growth per device per year, and what the volume actually sustains versus what is configured. Every figure is measured from the running system — deriving the sample rate from `polling_schedule` was tried and was wrong by 85×, because schedules mix 30 s ICMP with 6-hourly sync.

## Non-negotiable decisions

All architecture decisions live in **`DECISIONS.md`** with rationale. Never silently contradict one; if a decision needs revisiting, propose a change there first. Headlines:

- Go backend, React+TS frontend, VictoriaMetrics + PostgreSQL + Redis + RabbitMQ, REST API, GitHub Actions CI. Deployment is **Docker Compose**; the on-prem Kubernetes/Helm target of ADR-006 is paused by ADR-024.
- v1 scope: SNMP v2c/v3 collection of interface traffic, device health, ICMP availability, inventory — for Cisco, Juniper, Huawei, ZTE, Ubiquiti, Ruckus, and (ADR-021) Fortinet FortiGate and Palo Alto PAN-OS. Firewalls are in scope as *devices* plus device-level session gauges (`netinv_firewall_*`); anything policy-, rule-, NAT- or VPN-scoped stays deferred. **Weathermap editor is the v1 flagship.**
- Explicitly deferred: firewall/NAT/LB metrics, syslog ingestion and SNMPv3 traps (v1/v2c traps are in, ADR-025), Keycloak, multi-tenant activation, HA. Deferred ≠ ignored: the design keeps seams for each. **Wireless is now partly in scope** — controller-level client and AP counts only, per ADR-018; per-client and RF metrics remain deferred.
- Clean Architecture + DDD bounded contexts + CQRS-lite (separate read/write paths, single Postgres). Connector plugin framework with compile-time registration (no Go `plugin` package).
