Query the running deployment for them.
- **Validated against real hardware** (risk R-07, partially closed): `ubiquiti` and `generic` on UDM-Pro/UCG-Ultra, `ruckus` on an R710. Each is documented in doc 10 with what the device *actually* exposes — including what it does not. **`cisco-ios`, `juniper-junos`, `huawei-vrp`, `zte-zxr`, `fortinet-fortios` and `paloalto-panos` remain unvalidated against real units — six of the eight connectors.**
- **Flow collection exists but is narrow (ADR-020, doc 34).** `netinv-flow` listens on UDP 2055, decodes **NetFlow v5, v9 and IPFIX** (ADR-022; sFlow still unread) on UDP 2055 and 4739, and aggregates at ingest into top-N talkers/conversations/applications per interface — `netinv_flow_bytes` and `netinv_flow_packets`. Raw per-flow storage stays deferred; a bucket outside the top N was never written, not merely unqueried. sFlow needs its own decoder and shares none of the template machinery. The **Flow tab** on device detail and the **Top flow** dashboard panel read the series through the metrics proxy — note `netinv_flow_bytes` is *not* cumulative, so `rate()` silently under-reports it; use `flowRateExpr`/`flowWindow` from `api/hooks.ts`. The per-vendor exporter setup guide is duplicated in doc 34 §4.2 and `features/devices/FlowSetupGuide.tsx`; change both together. **A pilot UniFi gateway now exports NetFlow v5 and it decodes end to end** (2026-08-12, doc 34 §4.2) — the first real-hardware flow validation. UniFi Network has native flow export under Traffic Logging (v5/v9/IPFIX); the earlier claim here and in doc 34 that UniFi *cannot* export flow was inferred from a missing sFlow MIB and was simply wrong. Two of its defaults matter: sampling is **on** (Hash 1-in-512) and Timeout Rate — the active timeout — is 5 minutes, so exports arrive in bursts. Turning sampling off took the pilot from 7 minutes of data in 45 to 27 in 30. **Flow totals are a fraction of the SNMP counters and that is by design** — measured at 3.3%/10.5% on two interfaces, dominated by the top-N cut, which was confirmed saturated at its ten-bucket cap in every interval. Sampling scale is verified against captured headers (`mode=2 interval=512` sampled, `mode=0 interval=0` off), so the gap is ADR-020's design, not a decode error: SNMP is the authority for volume, flow for composition. Export is selected **per network**, not per interface, and an unticked network is silently absent. Gateways export from their **WAN address, not their management IP**, so devices carry a `flow_exporters` list (doc 34 §3.1) that the Flow tab can claim addresses into; building a multi-address selector needs `reQuote` from `api/hooks.ts`, because MetricsQL unescapes the string before compiling the regex and a single backslash is rejected as an invalid escape. v9, IPFIX, IPv6 and options-record sampling are still validated only against a generated source. The two firewall connectors from ADR-021 both export v9 and can now feed it — a real exporter is the most useful thing an outside contributor could test. **v9 and IPFIX make the collector stateful** — a data record is meaningless without the template describing it, so a restart loses every template and flow stays missing until exporters resend (10-20 min). That window is counted as `awaiting_template`, deliberately *not* as "undecodable", so nobody hunts a fault that is not there. Three traps cost time and are worth knowing: VictoriaMetrics hides samples newer than 30 s from instant queries (`-search.latencyOffset`), so a "did my write land" check right after a drain returns zero and looks like a broken writer; and the collector is deliberately quiet when idle, so "no log output" means nothing is arriving, while a misconfigured exporter logs `flow intake` at info.
- **What remains for v1.0:** real-hardware validation of the four untested vendor connectors, 72 h soak + chaos-lite on staging k8s, the doc 20 §12 security checklist against TLS, and a backup/restore drill on the pilot data. These need real infrastructure and time — do not fake them.
- **Recurring lesson worth reading before touching metrics code:** MetricsQL `or` matches on labels *excluding* `__name__`, so two metrics that differ only by name collapse into one and the second disappears silently. This has now caused three separate bugs (traffic in/out, memory used/total, AP up/total). Combine named metrics through `trafficExpr`/`seriesExpr` in `frontend/src/api/hooks.ts`, never a bare `or`.
- **Deploying anywhere other than this dev box:** `deploy/compose-app/quickstart.sh` is the whole stack on one host (doc 32); `deploy/proxmox/netinv-lxc.sh create|verify|destroy` builds it in a Proxmox LXC and is also the intended way to test a branch against real hardware without touching a live instance (doc 33 §7). One thing does not carry over from a normal Docker host: inside an unprivileged LXC, Docker clamps `net.ipv4.ping_group_range` to a single gid that is not the poller's, so ICMP silently stops while SNMP keeps working. The compose file sets the range per container to fix it — do not remove that `sysctls:` block.

- **Deployment settings that the UI and the API must agree on.** Three values are configurable and each has a coupling that breaks silently if it drifts:
  - `NETINV_VM_RETENTION` (default **2y**) is read by *both* VictoriaMetrics and the API — the API rejects range queries beyond it with 422 rather than clamping, so a ceiling below actual retention hides data the operator is paying to keep. Shipping the Cacti presets against a hard-coded 90-day ceiling made "Last Year" return an error instead of a chart; that is why they are one setting.
  - **Poll cadence** is editable fleet-wide from Platform → Pollers (1/5/10/15 min, `PUT /platform/polling`). It writes `polling_schedule` as well as the profile, because the scheduler reads the schedule. `rate()` lookbacks are sized from it — a lookback shorter than the cadence spans one sample and returns nothing, blanking every traffic chart with no error.
  - `GET /metrics/limits` reports both (`max_range_s`, `poll_interval_s`) so the frontend never hard-codes either. If you add a chart, size its rate window with `rateWindow(step, pollS)` from `api/timerange.ts`.
- **Graphs share one time range** (`api/timerange.ts`): Cacti's nineteen timespans, default "Last Day", persisted in localStorage, applied to every chart including the weathermap hover card. Step and rate window scale with the span. Presets past retention are shown disabled, not hidden.
- **Platform → Capacity** (`GET /platform/capacity`) answers "will the disk hold this retention": disk used/free, measured bytes-per-sample, growth per device per year, and what the volume actually sustains versus what is configured. Every figure is measured from the running system — deriving the sample rate from `polling_schedule` was tried and was wrong by 85×, because schedules mix 30 s ICMP with 6-hourly sync.

## Non-negotiable decisions

All architecture decisions live in **`DECISIONS.md`** with rationale. Never silently contradict one; if a decision needs revisiting, propose a change there first. Headlines:

- Go backend, React+TS frontend, VictoriaMetrics + PostgreSQL + Redis + RabbitMQ, REST API, on-prem Kubernetes, GitHub Actions CI.
- v1 scope: SNMP v2c/v3 collection of interface traffic, device health, ICMP availability, inventory — for Cisco, Juniper, Huawei, ZTE, Ubiquiti, Ruckus, and (ADR-021) Fortinet FortiGate and Palo Alto PAN-OS. Firewalls are in scope as *devices* plus device-level session gauges (`netinv_firewall_*`); anything policy-, rule-, NAT- or VPN-scoped stays deferred. **Weathermap editor is the v1 flagship.**
- Explicitly deferred: firewall/NAT/LB metrics, NetFlow, syslog/trap ingestion, Keycloak, multi-tenant activation, HA. Deferred ≠ ignored: the design keeps seams for each. **Wireless is now partly in scope** — controller-level client and AP counts only, per ADR-018; per-client and RF metrics remain deferred.
- Clean Architecture + DDD bounded contexts + CQRS-lite (separate read/write paths, single Postgres). Connector plugin framework with compile-time registration (no Go `plugin` package).

## How to work in this repo

1. **Read before writing:** `DECISIONS.md`, then the specific doc you're touching, then adjacent docs it cross-references.
2. **Docs are the source of truth.** When code exists later, code must follow docs; if reality diverges, update the doc in the same commit.
3. Each doc in `docs/` has a frontmatter-style header (`Status`, `Depends on`). Keep statuses honest: `draft` → `review` → `approved`.
4. Mermaid for all diagrams. Markdown tables for schemas/APIs. No binary artifacts in `docs/`.
5. Conventional commits (`docs:`, `feat:`, `fix:`, `chore:`). One logical unit per commit.
6. Terminology is defined in `docs/16-domain-model.md` (ubiquitous language). Use those exact terms — e.g. a *Device* is a managed network element; a *Poller* is a site-local collection agent; a *Connector* is a vendor driver.
